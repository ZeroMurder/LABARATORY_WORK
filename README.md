# Лабораторная работа №1

## Управление конфигурацией среды исполнения ПО с помощью системных политик реестра

### Цель работы

Изучить механизм хранения параметров групповых политик в системном реестре Windows, освоить ручное создание и удаление параметров политик с помощью командной строки, а также проверить результат применения созданной конфигурации.

---

## Ход выполнения работы

### 1. Исследование исходного конфигурационного состояния

На виртуальной машине был подключён накопитель, доступный в системе как диск `E:`.

Для проверки исходного состояния была выполнена попытка записи файла на данный диск.

Команды выполнялись из командной строки с повышенными правами:

```cmd
E:

echo TEST_BEFORE > E:\test_before.txt

dir E:\
```

В результате был создан файл `test_before.txt`, что подтвердило возможность записи на диск до применения политики.

### 2. Программирование политики через системный реестр

Для проверки механизма запрета записи была создана политика в системной ветке:

```text
HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices
```

Для класса устройств, идентифицируемого GUID

```text
{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}
```

был создан параметр `Deny_Write` типа `REG_DWORD` со значением `1`.

Команда создания параметра:

```cmd
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices\{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}" /v Deny_Write /t REG_DWORD /d 1 /f
```

После этого содержимое созданного раздела было проверено командой:

```cmd
reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices\{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}"
```

В результате система отобразила параметр:

```text
Deny_Write    REG_DWORD    0x1
```

Таким образом, наличие заданного значения политики в реестре было подтверждено.

### 3. Применение политики и проверка результата

Для принудительного обновления групповых политик была выполнена команда:

```powershell
gpupdate /force
```

После обновления политики процесс Проводника Windows был перезапущен:

```powershell
Stop-Process -Name explorer -Force
Start-Process explorer
```

После этого была повторно выполнена попытка записи файла:

```cmd
echo TEST_AFTER > E:\test_after.txt
```

### Результат проверки

В рассматриваемой виртуальной среде VirtualBox накопитель `E:` был представлен операционной системе как виртуальный диск, поэтому созданная политика класса **Removable Storage Devices** не обеспечила ожидаемую блокировку операции записи.

Файл `test_after.txt` был создан успешно.

Данный результат необходимо рассматривать отдельно от проверки самого механизма конфигурации политики: наличие параметра `Deny_Write` в соответствующей ветке реестра было подтверждено командой `reg query`, то есть конфигурационный параметр был создан корректно.

Таким образом, эксперимент одновременно показал:

* корректное создание параметра политики;
* корректное наличие параметра в системной ветке реестра;
* обновление конфигурации групповой политики;
* зависимость фактического результата от способа представления устройства виртуальной машиной.

# Ответы на инженерные вопросы

## 1. Почему изменения в HKLM\SOFTWARE\Policies работают как политики Windows без gpedit.msc?

`gpedit.msc` не является самим механизмом групповой политики. Это графический интерфейс редактора локальных групповых политик, предоставляющий администратору удобный способ изменения поддерживаемых параметров.

Параметры политик Windows в конечном итоге представлены в системной конфигурации, в том числе в специальных ветках реестра:

```text
HKLM\SOFTWARE\Policies
HKCU\SOFTWARE\Policies
```

При обработке политик соответствующие системные компоненты используют эти параметры независимо от того, были ли они созданы через графический интерфейс или другим способом.

Поэтому отсутствие `gpedit.msc` само по себе не означает отсутствие механизма обработки политик. Ручное изменение конкретного поддерживаемого параметра в ветке `Policies` может изменить поведение соответствующего системного компонента.

При этом важно различать **сам механизм обработки политики** и **графический редактор**, который является лишь инструментом администрирования.

---

## 2. Какую проблему совместимости решает LUA File Virtualization?

Механизм **LUA File Virtualization** предназначен прежде всего для совместимости со старыми приложениями, которые были разработаны с расчётом на возможность записи в защищённые системные каталоги, например:

```text
C:\Program Files
C:\Windows
```

Современные версии Windows ограничивают запись в такие каталоги для обычных пользователей.

Для некоторых совместимых legacy-приложений система может использовать виртуализацию файлов: попытка записи приложения перенаправляется в пользовательское виртуализированное хранилище, связанное с:

```text
%LOCALAPPDATA%\VirtualStore
```

Таким образом, приложение может продолжать работать без предоставления ему административных прав и без непосредственной записи в защищённый системный каталог.

Механизм является средством совместимости и не следует рассматривать его как универсальный способ обхода механизмов безопасности Windows.

---

## 3. Что такое RSoP и для чего используется gpresult?

**RSoP (Resultant Set of Policy)** — это результирующий набор параметров групповых политик, который фактически применяется к определённому пользователю или компьютеру после обработки доступных политик.

В доменной инфраструктуре на итоговую конфигурацию могут влиять политики различных уровней, например:

* локальные политики;
* политики сайта;
* политики домена;
* политики подразделений (OU).

При наличии нескольких политик необходимо определить, какие параметры фактически применились и какие настройки имеют приоритет.

Для диагностики используется команда:

```powershell
gpresult
```

Она позволяет получить сведения о:

* применённых групповых политиках;
* конфигурации компьютера;
* конфигурации пользователя;
* параметрах безопасности;
* результатах обработки политик;
* возможных проблемах применения.

Например, при развёртывании нового программного комплекса `gpresult` позволяет определить, не ограничивает ли работу приложения существующая корпоративная политика.

Это делает инструмент особенно полезным при диагностике ситуаций, когда локально программа настроена правильно, но в корпоративной среде её поведение отличается.
