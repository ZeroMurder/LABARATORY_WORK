# Предварительный этап

## Создание точки восстановления

Перед началом работы с реестром и системными политиками решил сначала сделать точку восстановления. Это нужно на случай, если после изменения системных параметров что-то пойдет не так.

Для этого:

1. Открыл `sysdm.cpl`.
2. Перешел в раздел **«Защита системы»**.
3. Проверил и включил защиту системного диска `C:`.
4. Создал точку восстановления **«Перед лабораторной по ПМ04»**.

# Лабораторная работа №1

## Управление конфигурацией через системные политики реестра

### Цель

Посмотреть, как Windows хранит параметры групповых политик в реестре, попробовать изменить такую политику вручную через командную строку и проверить, что после этого изменилось в системе.

---

## 1. Проверка состояния до применения политики

Для эксперимента использовал виртуальный диск `E:`.

Сначала нужно было убедиться, что запись на него вообще работает. Поэтому открыл командную строку от имени администратора и выполнил:

```cmd
E:

echo TEST_BEFORE > E:\test_before.txt

dir E:\
```

В результате файл `test_before.txt` создался.

То есть до изменения политики запись на диск работала нормально.

---

## 2. Создание политики через REG

Дальше решил не использовать графический редактор, а прописать параметр непосредственно в реестре.

Использовалась ветка:

```text
HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices
```

Для нужного класса устройств был создан раздел с GUID:

```text
{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}
```

Команда:

```cmd
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices\{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}" /v Deny_Write /t REG_DWORD /d 1 /f
```

Здесь создается параметр `Deny_Write` типа `REG_DWORD` со значением `1`.

После этого проверил, действительно ли запись появилась:

```cmd
reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices\{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}"
```

В выводе получил:

```text
Deny_Write    REG_DWORD    0x1
```

То есть сам параметр в реестре создался правильно.

---

## 3. Применение политики

После изменения реестра нужно было обновить групповые политики:

```powershell
gpupdate /force
```

После этого перезапустил Explorer:

```powershell
Stop-Process -Name explorer -Force
Start-Process explorer
```

Затем снова попробовал записать файл:

```cmd
echo TEST_AFTER > E:\test_after.txt
```

Файл создался.

На первый взгляд может показаться, что политика не сработала. Но здесь есть нюанс именно с VirtualBox.

В моей виртуальной машине подключенный накопитель фактически представлен Windows как виртуальный диск, а не как обычное USB-устройство того класса, на который рассчитана данная политика. Поэтому параметр `Deny_Write` в реестре присутствует, но сама операция записи этим конкретным устройством не блокируется.

Для меня это как раз показало разницу между двумя вещами:

* параметр политики действительно существует в системе;
* конкретное устройство действительно попадает под действие этой политики.

В данном случае первое подтвердилось, а второе — нет.

---

## 4. Удаление политики

После эксперимента вернул систему обратно.

Удалил созданный раздел:

```cmd
reg delete "HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices\{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}" /f
```

В консоли появилось:

```text
The operation completed successfully.
```

После этого снова перезапустил Explorer:

```powershell
Stop-Process -Name explorer -Force
Start-Process explorer
```

# Лабораторная работа №2

## Диагностика результирующих политик (RSoP)

### Цель

Получить информацию о реально примененных политиках Windows, посмотреть результаты через `gpresult` и дополнительно проверить некоторые системные параметры с помощью PowerShell.

---

## 1. Получение XML-отчета

Сначала создал отдельную папку для результатов:

```powershell
New-Item -ItemType Directory -Path "C:\GP_Reports"
```

После этого сформировал XML-отчет:

```powershell
gpresult /x C:\GP_Reports\gpreport.xml /f
```

В результате появился файл:

```text
C:\GP_Reports\gpreport.xml
```

XML удобен тем, что его можно не только открыть вручную, но и потом обработать скриптом.

---

## 2. HTML-отчет

Для обычного просмотра сделал еще HTML-версию:

```powershell
gpresult /h C:\GP_Reports\report.html /f
```

Открыл ее командой:

```powershell
Start-Process "C:\GP_Reports\report.html"
```

В браузере можно уже нормально посмотреть сводку по политикам и понять, какие настройки применились.

По результатам просмотра отчета проблем с применением политик обнаружено не было.

---

## 3. Дополнительная проверка через PowerShell

Дальше проверил локальные учетные записи:

```powershell
Get-LocalUser |
    Select-Object Name, Enabled, PasswordRequired, LastLogon
```

Команда вывела список пользователей и их основные параметры.

Также отдельно посмотрел параметры `luafv`:

```powershell
Get-ItemProperty -Path "HKLM\SYSTEM\CurrentControlSet\Services\luafv" |
    Select-Object Start, DisplayName
```

В результате получил:

```text
Start : 2
```

Также в выводе присутствует имя компонента:

```text
DisplayName : @%SystemRoot%\system32\luafv.dll,-100
```

То есть соответствующий системный компонент присутствует в конфигурации Windows.

# Ответы на вопросы для защиты

## 1. Почему изменение HKLM\SOFTWARE\Policies работает без gpedit.msc?

`gpedit.msc` — это графический инструмент для настройки локальных групповых политик. Сам механизм применения политик от этого редактора не зависит.

Windows использует специальные ветки реестра, в которых хранятся параметры политик, например:

```text
HKLM\SOFTWARE\Policies
HKCU\SOFTWARE\Policies
```

Поэтому если вручную создать правильный параметр в соответствующей ветке, Windows может использовать его так же, как параметр, созданный через редактор политики.

Получается, что `gpedit.msc` — это скорее удобная оболочка для администратора, а не сама Group Policy.

При этом нельзя просто записать любое значение в `Policies` и ожидать, что Windows его поймет. Параметр должен соответствовать конкретной поддерживаемой политике и иметь правильный путь, имя и тип.

---

## 2. Для чего нужен LUA File Virtualization?

Это в первую очередь механизм совместимости со старыми программами.

Раньше некоторые приложения могли напрямую пытаться писать, например, в:

```text
C:\Program Files
C:\Windows
```

В современных Windows обычный пользователь не должен иметь возможность просто так изменять эти каталоги.

Если старое приложение не рассчитано на такую модель безопасности, оно может получить `Access Denied`.

Для некоторых legacy-приложений Windows может использовать виртуализацию файлов. Запись перенаправляется в пользовательское хранилище, связанное с:

```text
%LOCALAPPDATA%\VirtualStore
```

Программа при этом может продолжать работать, хотя фактически запись происходит не туда, куда она первоначально пыталась писать.

Это именно механизм совместимости, а не способ выдачи приложению административных прав.

---

## 3. Что такое RSoP и зачем нужен gpresult?

RSoP — **Resultant Set of Policy**, то есть фактически получившийся набор политик после обработки всех применяемых правил.

Если политик несколько, недостаточно просто знать, что какая-то политика существует. Нужно понять, какая из них реально применились к компьютеру или пользователю.

Именно для этого удобен `gpresult`.

Например, если в организации устанавливается новая программа, а она внезапно не может выполнить какую-то операцию, можно проверить:

* какие политики применились;
* какие параметры получил компьютер;
* какие параметры получил пользователь;
* не была ли нужная политика отфильтрована;
* не перекрывается ли настройка другой политикой.

Получается, `gpresult` позволяет смотреть на Windows не только с точки зрения «какие настройки существуют», а с точки зрения **«что реально получилось после применения всех политик»**.

# Вывод

В этих лабораторных работах я посмотрел на Group Policy не только через графический интерфейс, а со стороны самой системы.

В первой работе вручную создал параметр политики в реестре:

```text
HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices
```

После этого проверил его через `reg query`, обновил политики с помощью `gpupdate` и попробовал проверить результат на виртуальном диске.

Самое интересное здесь оказалось в том, что наличие параметра в реестре еще не означает, что конкретное устройство обязательно будет заблокировано. В VirtualBox накопитель оказался представлен Windows не так, как ожидалось для данной политики, поэтому запись на `E:` продолжила работать.

После эксперимента созданный параметр был удален.

Во второй работе уже занимался не изменением конфигурации, а ее просмотром. С помощью `gpresult` получил XML и HTML отчеты, а через PowerShell дополнительно посмотрел локальных пользователей и параметры `luafv`.

В результате я получил практическое представление о том, где Windows хранит параметры групповых политик, как их можно проверить и изменить из командной строки, а также как диагностировать результирующее состояние системы с помощью `gpresult` и PowerShell.
